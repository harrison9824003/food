# ERP 同步：Outbox Pattern 與 mock-erp

對應里程碑 6 第二段。

## 要解決的問題

訂位成立（或取消、付款成功…）之後要通知外部的 ERP／POS。直接在訂位的程式裡「寫完資料庫再呼叫 ERP」有兩個致命問題：

| 做法 | 出錯的情境 |
|---|---|
| 先呼叫 ERP、再寫資料庫 | ERP 通知了，但資料庫寫入失敗 → ERP 有一筆**不存在的訂位** |
| 先寫資料庫、再呼叫 ERP | 資料庫寫好了，呼叫 ERP 前程式當掉、或 ERP 剛好掛了 → ERP **永遠不知道這筆訂位** |
| 兩者都是：ERP 慢 | 顧客的訂位請求被拖慢，ERP 一掛，**整個訂位功能跟著掛** |

## Outbox Pattern

```
          ┌───────────── 同一個資料庫交易 ─────────────┐
訂位請求 → │ 佔名額、分配桌位、建立訂位 + 寫一筆 outbox 事件 │ → 提交
          └─────────────────────────────────────────────┘
                                                       │（回應顧客，到此為止，不碰 ERP）
                          排程每分鐘 ↓
                  OutboxDispatcher：領事件 → POST 到 ERP（帶冪等鍵）
                       ├─ 成功 → 標記已送出
                       ├─ 暫時失敗 → 指數退避後重試
                       └─ 重試用盡 / 被 ERP 拒絕 → 失敗清單（後台可手動重送）
```

- **同進同退**：事件和訂位異動寫在**同一個交易**（`OutboxRecorder`）。交易回滾，事件一起消失；交易提交，事件一定存在。
  `record()` 若不在交易內呼叫會直接拋例外——那是程式寫錯了，要在開發時就炸出來，而不是默默失去保證。
  有測試：桌位分配失敗導致訂位回滾時，outbox 裡也沒有事件。
- **ERP 不影響顧客**：顧客的請求完全不會等 ERP。ERP 掛一整天，訂位照常，事件在 outbox 裡排隊，恢復後自動補送。
- **at-least-once**：事件只要還在就一定會被送出（不會漏）；但可能被送出不只一次，所以 ERP 端要靠冪等鍵去重。

### 記錄哪些事件

| 事件 | 時機 |
|---|---|
| `reservation.created` | 訂位建立 |
| `reservation.status_changed`（含 `from`、`to`） | 付款成功確認、顧客取消、後台標記已到／未到／取消、逾時釋放、晚到付款補回 |

事件內容是**變更後的完整快照**（訂位代號、門市、日期時間、人數、聯絡人、預點餐點、狀態…），不是差異：
接收端不必回頭問我們，重送或亂序到達時每個事件也都各自完整。

冪等的重複請求（連點兩次取消）**不會**記錄第二筆事件（有測試）。

## 投遞（`OutboxDispatcher`，指令 `outbox:dispatch`，每分鐘一次）

### 領取：三個條件缺一不可

1. 狀態是 `pending` 且到了 `next_attempt_at`。
2. **同一張訂位比它早的事件都已經送成功。** 否則 ERP 會先收到「取消」再收到「建立」。早的事件若失敗、還在等重試或等人處理，後面的就跟著等——寧可慢，不要亂序。不同訂位互不影響。
3. **沒被別的 worker 領走**：`SELECT … FOR UPDATE SKIP LOCKED`，多個 worker 同時跑時各自拿到不同的列、互不等待。
   （Laravel 的查詢建構器沒有 `skipLocked()`，要用 `->lock('for update skip locked')`；測試會檢查實際送出的 SQL 真的帶有 `skip locked`。）

領到之後，先把 `next_attempt_at` 往後推一個**租約**（120 秒）並累計嘗試次數，才離開交易去呼叫 ERP，所以**不必在持有資料庫鎖的情況下等 HTTP 回應**。
worker 若在送到一半時當掉，租約到期後事件會被重新領取；那次當掉也已經算一次嘗試，不會因為一直當掉而無限重試。

一輪會持續領取直到沒有可送的事件（或用完 50 秒預算），所以「建立 → 確認」這種同一張訂位的連續事件在同一次排程內就送完，不必一筆等一分鐘。

### 冪等：`Idempotency-Key`

每次請求帶 `Idempotency-Key: outbox-{事件 id}`，同一筆事件不論重送幾次都是同一個鍵。
最棘手的情境是**「ERP 已經處理了，但回應遺失」**：我們只看到逾時，無從得知 ERP 有沒有處理，只能重送。沒有冪等鍵，ERP 就會多出一筆重複的訂位。

### 重試與失敗

| ERP 的回應 | 判斷 | 處理 |
|---|---|---|
| 2xx | 成功 | 標記已送出 |
| 408、429、5xx、連線失敗、逾時 | **暫時性**，等一下可能就好 | 指數退避後重試 |
| 其他 4xx（400、404、422…） | **永久性**，是我們送的東西有問題，重試只會得到一樣的結果 | 直接進失敗清單，不浪費重試次數 |

- **指數退避**：第 n 次失敗後等 `60 × 2^(n-1)` 秒（1、2、4、8、16 分鐘），再加 **±20% 隨機抖動**。
  抖動的用意：ERP 當機一小時後恢復，累積的幾百筆事件若都在整數分鐘同時重試，會一次把剛恢復的 ERP 壓垮。
- **最多 6 次**（`ERP_MAX_ATTEMPTS`），用盡後進入**失敗清單**，不再自動重試。
- 沒預期到的例外（我們自己的 bug）也當成暫時性失敗，不會讓整批卡住。
- 狀態更新都是**條件式**（`WHERE status = 'pending'`）：手動重送與正在進行的投遞同時發生時，不會互相覆蓋。

## 後台：ERP 同步（總部與店長）

「ERP 同步」頁：失敗／待送（重試中）／已送出三個分頁與各自的數量，每 15 秒自動更新。
每筆顯示訂位代號、事件、嘗試次數（`3 / 6`）、下一步（「約 4 分鐘後重試」）、最後的錯誤訊息。**不顯示事件內容**（含顧客手機）。

- 失敗的事件可「**重送**」；還在等退避的可「立即重試」。重送不是直接呼叫 ERP，而是把事件改回「立刻可送」、嘗試次數歸零，由排程撿走——
  這樣後台請求不會被慢的 ERP 拖住，也和自動重試走同一條路徑。嘗試次數不歸零的話，下一次失敗就會立刻再回到失敗清單。
- **已經送出的事件不可重送**（`409 ALREADY_SENT`），否則 ERP 會收到第二次通知。
- 權限：總部看全部、店長只看自己門市（事件記有 `store_id`）、**店員不可**。見 [permissions.md](permissions.md)。

`GET /api/admin/outbox-events?status=failed|pending|sent`、`POST /api/admin/outbox-events/{id}/retry`

## mock-erp（`/mock-erp`，Node.js）

刻意做成不可靠，用來展示上面所有機制：

| 行為 | 說明 |
|---|---|
| 隨機失敗 10% | 事件處理**之前**就回 408 |
| 回應遺失 5% | 事件**已處理**卻回 504 —— 驗證冪等 |
| 冪等 | 同一個 `Idempotency-Key` 再來一次，回成功但標記 `duplicate: true`，不重複套用 |
| 亂序偵測 | 同一張訂位收到序號較小的事件，記錄 `out_of_order` |
| 整個關閉 / 拒絕 | `mode: down` 全部回 503；`mode: reject` 全部回 422（永久性失敗） |

```bash
curl localhost/mock-erp/control                                    # 目前設定
curl -X POST localhost/mock-erp/control -H "Content-Type: application/json" \
     -d '{"mode":"down"}'                                           # 關閉 ERP（normal | down | reject）
curl -X POST localhost/mock-erp/control -H "Content-Type: application/json" \
     -d '{"failureRate":0,"lostResponseRate":1}'                    # 調整機率
curl localhost/mock-erp/events                                      # 已套用的事件
curl localhost/mock-erp/stats                                       # 收到幾次、套用幾次、擋掉幾次重複
curl -X POST localhost/mock-erp/reset                               # 清空並恢復預設
```

資料放在記憶體，容器重啟就清空。

## 實測（對真實的 mock-erp 容器）

| 情境 | 結果 |
|---|---|
| 正常 | 建立、取消共 3 筆事件全部送出，ERP 收到的順序正確，`out_of_order=false` |
| 回應遺失 | 第一次 ERP 處理了但回 504 → 我們排重試；第二次重送 → ERP 統計：**收到 2 次、實際套用 1 次、重複被擋掉 1 次**，ERP 只有 1 筆事件 |
| ERP 關閉 | 「建立」失敗 3 次後進入失敗清單；同一張訂位的「取消」**沒有越過它**（仍是待送、0 次嘗試） |
| 恢復 | ERP 恢復後在後台重送 → 排程依序送出「建立」再「取消」，順序正確；對已送出的事件再按重送回 409 |

這是用縮短的退避（`ERP_BACKOFF_BASE=1`）與較小的上限（`ERP_MAX_ATTEMPTS=3`）跑的，正式設定是 1、2、4、8、16 分鐘與 6 次。

## 日誌

獨立的 `erp` channel（`storage/logs/erp-YYYY-MM-DD.log`，保留 30 天）：每次投遞的成功、失敗與下次重試時間、放棄的原因、手動重送（含操作者）。
**不寫入事件內容**（含顧客手機），只記事件編號、類型、訂位編號、嘗試次數與錯誤訊息。

```bash
docker compose exec php-fpm sh -c "grep 'event_id\":5' storage/logs/erp-*.log"   # 追某一筆事件的完整經過
```

## 設定

| 環境變數 | 預設 | 說明 |
|---|---|---|
| `MOCK_ERP_URL` | `http://mock-erp:3000` | ERP 位址 |
| `MOCK_ERP_TIMEOUT` | `5` | 單次請求逾時秒數 |
| `ERP_MAX_ATTEMPTS` | `6` | 失敗幾次後進入失敗清單 |
| `ERP_BACKOFF_BASE` | `60` | 指數退避的基準秒數 |

批次大小與租約秒數在 `config/erp.php`。

## 限制

- 排程每分鐘一次，所以事件最多晚約一分鐘送到 ERP；需要更即時可以改成常駐 worker，目前沒有做。
- 失敗事件會擋住同一張訂位後面的事件（為了順序）；這是刻意的取捨，後台清單上看得到。
- outbox 的已送出事件目前**不會自動清理**，量大時需要定期刪除舊資料（例如保留 30 天）。
- 事件只記訂位；付款與退款不會通知 ERP（退款流程會在第三段加入事件）。

## 測試

```bash
docker compose exec php-fpm php artisan test --filter=Outbox
```

涵蓋：記錄（同進同退、快照、狀態變更、冪等請求不重複記錄）、投遞（成功、退避增長、上限、永久性失敗、各種 HTTP 狀態分類、
連線失敗、例外隔離、冪等鍵穩定、依序、不同訂位互不阻擋、領取租約、`skip locked`）、後台（清單、權限、重送、已送出不可重送、排程）。

> 「同時有兩個 worker」無法在單一 PHPUnit 行程內真正並行重現，所以測試驗證的是領取的**效果**（租約讓第二次領取拿不到同一筆）與實際送出的 SQL，
> 而不是真的開兩個行程。
